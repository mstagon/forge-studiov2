1. 두 정체성 — Run vs Composition

v0.4.0 의 가장 큰 구조 변화. \"Team\" 단일 개념을 두 정체성으로 분리. Run = 워크스페이스 안에서 진행 중인 인스턴스, Composition = 글로벌 재사용 템플릿. 0.5.3 부터 Council 이라는 세 번째 정체성이 추가됨.

RUN
인스턴스 (워크스페이스 스코프)

이 워크스페이스에서 지금 돌아가는 N명 agent + worktree + 진행도. <wsPath>/.claude/teams/<id>/config.json

UI 위치

Workspace 패널 좌측 \"Teams\" 섹션 → 카드 클릭 → 풀스크린 RunLiveView

COMPOSITION
템플릿 (글로벌 재사용)

\"이런 멤버 조합으로 일하는 패턴\" 재사용 단위. ~/.claude/team-compositions/<name>.json

UI 위치

Library 사이드바 → Compositions 탭 → \"Apply to workspace\" → Wizard prefilled

COUNCIL · 0.5.3
토론 (다중 모델)

같은 task 를 N개 모델 (Claude Opus + Codex + Sonnet 등) 이 보고 토론 라운드 → 합의 / 의견 차이 노출

UI 위치

RunLiveView 의 새 \"Discussion\" 탭 + Wizard Step 2 \"Council mode\" 토글 (계획)

왜 분리? Run 은 git worktree 에 묶여 한 워크스페이스 안에서만 의미 있고, Composition 은 \"다음 프로젝트에서 또 쓰고 싶은 멤버 조합\" 이라 글로벌이어야 한다. Council 은 \"같은 작업을 여러 모델이 비교\" 라는 또 다른 차원.

3. 데이터 모델 — config.json

팀이 디스크에 어떻게 저장되나. chokidar 가 이 파일을 감시 → 변경 감지 → store 자동 갱신 → UI 즉시 반영.

<workspace>/.claude/teams/<teamId>/config.json
{
  "id": "team-1746604800123-a3f9b2",
  "name": "회원가입 피처 팀",
  "goal": "이메일/소셜 로그인 + 온보딩 3단계",
  "workspaceId": "ws-forge",
  "worktreeStrategy": "isolated",  // "isolated" | "shared"
  "mergeStrategy": "squash",         // "squash" | "sequential"
  "baseBranch": "team/team-1746604800123-a3f9b2",
  "status": "active",                    // active | paused | idle | blocked | done
  "createdAt": 1746604800123,
  "members": [
    {
      "agentId": "architect",
      "task": "auth flow ADR 작성",
      "state": "done",                  // active | done | blocked | queued | idle
      "branch": "team/team-.../architect",
      "worktreePath": "<ws>/.claude/teams/team-.../worktrees/architect",
      "tmuxPaneId": "forge-team-team-...-architect:0.0",
      "tokens": 22400,
      "files": 3
    },
    { ... 나머지 멤버 ... }
  ]
}

chokidar 가 <wsPath>/.claude/teams/ 디렉터리를 감시. 새 config.json 생성/수정/삭제 → AgentTeamWatcher 가 캐시 갱신 → 'change' 이벤트 emit → renderer 의 useAgentTeamStore subscribe 콜백이 list 재로드 → UI 즉시 반영.

6. Wizard 4-step

Workspace 패널 \"+\" 또는 ⌘N → 모달 → 4 단계.

Step 1
이름 + 목표

팀 이름 (필수) + 자연어 한 줄 목표 (옵션)

예: \"회원가입 피처 팀\"
Step 2
멤버 선택

18 agent 풀에서 chip multi-select. 0.5.3 부터 같은 agent 의 다른 모델 사본 가능

3~7 명 권장
Step 3
전략

worktree (isolated/shared) + merge (squash/sequential) — 각 옵션 옆 한 줄 설명

기본: isolated + squash
Step 4
확인

예상 동작 표시 (\"5명 분리 worktree + 5개 tmux 세션 spawn\")

→ Start

전략 옵션 — 결정 가이드

옵션의미언제
Isolated worktree멤버별 git worktree + tmux 세션 자동 spawn멤버 ≥ 2명, 동시 다른 영역 작업
Shared worktree같은 worktree 공유소규모 팀 (1~2명) 또는 sequential 작업
Squash merge모든 멤버 작업을 한 커밋으로 합침피처 전체를 한 커밋으로 보고 싶을 때
Sequential merge멤버 순서대로 머지 (history 보존)각 멤버 기여를 별도 커밋으로 추적

7. create() — worktree + tmux 자동

Wizard \"Start\" 클릭 시 일어나는 모든 일. 풀 라운드트립.

Create flow — Wizard → AgentTeamWatcher.create() → live UI
Graceful degradation: git/tmux 미설치 환경에서는 단계 3~6 이 skip 되고 config.json 만 작성됨. hasGit()/hasTmux() 사전 검사. Path traversal 방지: isPathInside(teamRoot, worktreePath) + agentId 정규식 sanitize [^A-Za-z0-9_-].

8. Run 라이브뷰 — 4영역 풀스크린

Workspace 패널의 Run 카드 클릭 시 메인 영역 전체가 풀스크린으로 전환. 777genius 레퍼런스 차용.

RunLiveView Layout · 회원가입 피처 팀 (5 members)

인터랙션

  • 멤버 카드 클릭 → 그 agent 의 pane 이 grid 에서 강조/확대 (focus mode)
  • pane 더블클릭 → 풀스크린, ESC 로 그리드 복귀
  • Activity Feed 항목 클릭 → 해당 파일 diff 인라인
  • 멤버 카드 우상단 ⏸/▶ → pauseMember / resumeMember
  • 멤버 \"터미널\" 아이콘 → 그 멤버의 tmux 세션 attach (새 터미널 탭)

멤버 state 시각

active

초록 도트 + pulse · 진행 중

done

회색 도트 · 작업 완료

blocked

빨강 도트 + pulse · 결정/입력 대기

queued

회색 도트 (no pulse) · 의존성 대기

paused

노랑 · 사용자가 일시정지

idle

대기 (할당 X)

9. Pause / Resume — tmux detach

실제로 tmux 세션을 kill 하지 않음. detach-client 만 — agent 의 작업 컨텍스트 (history, 진행 중 커맨드) 그대로 유지.

pause(teamId)
전체 일시정지

모든 멤버 tmux 에 detach-client 보냄. config 의 status: 'paused'. 멤버별 state 도 'idle' 로

resume(teamId)
전체 재개

tmux 세션은 살아있으니 attach 만 끊긴 상태. status → 'active'. 사용자가 RunLiveView 열면 자동 재attach

pauseMember(teamId, agentId)
단일 멤버 일시정지

한 멤버의 tmux 만 detach. 다른 멤버는 계속 진행. 의존 멤버가 있으면 자동 queued 로

resumeMember(teamId, agentId)
단일 멤버 재개

해당 멤버 state → 'active'. 의존 해제된 다른 queued 멤버도 자동 활성화

10. Merge + 충돌 해결

팀 작업 끝나면 멤버 worktree 들의 변경을 베이스 브랜치 (team/<teamId>) 로 머지. 충돌 시 풀스크린 3-way diff 모달.

Merge flow — RunLiveView Merge 버튼 → AgentTeamWatcher.merge()

MergeConflictView — 3-way diff

풀스크린 오버레이 (z-index 200). 헤더 (충돌 카운트 + 닫기) + 좌측 충돌 파일 리스트 + 우측 3-column diff (ours / merged / theirs) + 푸터 액션 4개:

Use ours

베이스 브랜치 버전 채택

Use theirs

멤버 브랜치 버전 채택

Manual resolve

에디터 열기 + 직접 편집

Abort merge

머지 취소, 멤버 worktree 그대로

11. Remove — 단계별 cleanup

팀 삭제 = 디스크 정리 풀 체인. 각 단계 graceful — 실패해도 다음 단계 진행.

1
tmux kill-session

각 멤버의 forge-team-<id>-<agent> 세션 종료. 안 되면 다음으로

2
git worktree remove --force

각 멤버 worktree 디렉터리 정리. 변경 미커밋 있어도 force 로 제거

3
git branch -D team/<id>/<agent>

멤버 브랜치 삭제. 머지된 commit 도 brnach 만 사라짐

4
git branch -D team/<id>

베이스 브랜치 삭제

5
rm -rf <wsPath>/.claude/teams/<id>

config + 잔존 파일 통째 제거. chokidar 가 detect → store 갱신

주의: 5단계 모두 ignore-error. 어떤 단계가 실패해도 다음으로 진행. 결과는 \"부분 정리\" 가능 — 사용자가 직접 잔존 워크트리/세션 확인 필요할 수 있음.

12. 곧 — Council 마일스톤 (v0.5.3)

v0.5.2 까지가 \"한 모델 N명 멤버\" 라면, 0.5.3 은 \"한 task N개 모델\" — Council 패턴.

핵심 아이디어: 같은 task 를 Claude Opus + Codex GPT-5 + Sonnet 4.6 등 여러 모델이 보고 토론 라운드 → 합의 / 의견 차이를 사용자에게 노출.
Council Pattern (계획)

0.5.3 에서 추가될 것

Settings → Agent matrix

18 agents × 모델 dropdown — 워크스페이스별 override. 보안 감사는 Codex, 테스트 작성은 Haiku, UI 는 Opus 같은 식의 자유 매핑

Council Composition 타입

기존 Composition (멤버 = 다른 역할) + 새 타입 (멤버 = 같은 agent 다른 모델). Pre-built: \"Review council\", \"Implement comparison\", \"Architect council\"

Wizard Step 2 \"Council mode\" 토글

활성 시 멤버 선택 = 모델 다양화. Step 4 확인 화면에 \"3 model rounds\" 같은 요약

RunLiveView \"Discussion\" 탭

라운드별 발언 + 모델 배지 + 합의/반대 시각 분리. 합의 항목 ✓ / 충돌 항목 ⚠ 사용자 결정 highlight
